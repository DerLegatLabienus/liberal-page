# Meet Us — Scheduled Meetings with Cell Members

**Date:** 2026-06-12
**Status:** Approved design
**Backlog:** #15 ("Meet Us" — Scheduled Meetings with Cell Members)
**Depends on:** #3 User Accounts (shipped — Google sign-in + bearer JWT, `requireAuth`)

## Goal

A homepage **"Meet Us"** section, visible to **signed-in members only**, that lets a member book a meeting with people from the political cell via **Calendly**. Meetings happen externally (Zoom link auto-generated by Calendly, or in person); the app never hosts them and **stores no meeting data**. A member may hold **one active booking at a time**.

## Decisions (locked)

- **Architecture: stateless pull (Approach A).** No lock table, no webhooks. The one-active-booking rule is enforced by querying the Calendly API live at section load and again at booking time. Calendly is the single source of truth for bookings; our DB stores nothing about meetings. This is plan-agnostic — the query API works on Calendly's Free plan — and resolves backlog tension #1 in the strictest way ("no data" means *no rows at all*, not "minimal lock rows").
- **Why not the lock-table + webhook sketch (backlog tension #3/#5):** a lock table duplicates Calendly's state; webhooks (paid: Standard+) exist only to keep that duplicate in sync. Pulling on demand removes the state, the sync, the expiry job, the public signed endpoint, and the plan gating. Same pull-over-webhooks lesson as the Resend delivery-status change (2026-06-11).
- **Visibility: hidden unless signed in.** The section renders only for authenticated members (and only when the feature is enabled + configured).
- **Booking UI: embedded Calendly popup** (official embed script) over our page, prefilled with the member's name/email. No redirect.
- **Cancel/reschedule: on Calendly's own pages**, via the `cancel_url`/`reschedule_url` links we surface transiently. Cancelling on Calendly self-heals our gate (the next live query sees no active event and re-enables booking).
- **Host selection / meeting type (backlog tension #4): config, not code.** The Calendly **event-type URI** lives in admin-editable DB config. 1-on-1 with a fixed host (Free plan), round-robin rotation (Teams plan), or a fixed panel are all just different event types — switching is a config edit applied live, no deploy, no restart.
- **Dynamic config, no restarts:** runtime-changeable settings live in the DB (admin panel); only the secret API token is a Render env var.
- **Data residency (backlog tension #2):** "no data stored" means **our backend**. Calendly stores the booking (name, email, time) on its side — accepted and noted to users implicitly by booking through Calendly's UI.

## Configuration

| Setting | Where | Meaning |
|---|---|---|
| `CALENDLY_API_TOKEN` | Render env var (secret) | Personal access token. Unset ⇒ feature reports `configured: false`, section hides. Same no-op philosophy as `RESEND_API_KEY`. |
| `meetUs` feature flag | `feature_flags` table (existing) | `enabled` gates the section; `value` holds the **Calendly event-type URI** (e.g. `https://api.calendly.com/event_types/XXXX`). Admin-editable; takes effect immediately. |

**Accepted exposure:** the public `GET /api/feature-flags` endpoint returns flag values, so the event-type URI is visible. A Calendly event type maps to an inherently public booking page, so this leaks nothing sensitive; noted as a known limitation (below).

### Admin flag editing (small enabler)

The admin panel can currently read flags but not write them. Add:
- `PUT /api/admin/feature-flags/:name` (`requireAdmin`), body `{ enabled: boolean; value: string | null }` → `FeatureFlagsRepository.setFlag` (exists). `400` on non-boolean `enabled`.
- AdminPanel: a "Feature flags" section listing flags with an enabled checkbox + value input + Save (same pattern as the email-templates editor).

## Backend

### `server/services/calendly.ts` (new)

Lazy client over the Calendly v2 REST API (`https://api.calendly.com`), bearer `CALENDLY_API_TOKEN`. Mirrors the `getResend()` pattern: `getCalendlyToken(): string | null`, unset ⇒ callers report unconfigured; `_resetCalendly()` for tests.

- `isConfigured(): boolean` — token present AND `meetUs` flag has a non-empty event-type URI.
- `findActiveMeeting(email: string): Promise<ActiveMeeting | null>` where `ActiveMeeting = { startTime: string; cancelUrl: string; rescheduleUrl: string }`:
  1. `GET /scheduled_events?invitee_email=<email>&status=active&min_start_time=<now>&organization=<org-uri>` (org URI resolved once from `GET /users/me` and cached in-memory).
  2. If an event exists, `GET /scheduled_events/{uuid}/invitees` filtered by the email → take `cancel_url` / `reschedule_url`.
  3. Returned **transiently** to the caller; never written to the DB.
- `createSingleUseLink(): Promise<string>` — `POST /scheduling_links` with `{ max_event_count: 1, owner: <event-type URI from flag>, owner_type: 'EventType' }` → returns `booking_url`.
- **In-memory cache:** `findActiveMeeting` results cached per-email for 60 s (`Map`, like the bills cache) to avoid hammering Calendly on UI refreshes. Two staleness guards: the cache entry for a user's email is **busted on every `POST /booking-link`**, and callers can pass `fresh: true` to skip the cache entirely (used by the gate re-check and by the post-booking status refetch via `?fresh=1`).
- All Calendly HTTP errors are caught and logged (`[meetus]` prefix); callers receive a thrown typed error → routes translate to `502`.

### `server/routes/meetings.ts` (new, mounted at `/api/meetings`, all `requireAuth`)

- `GET /api/meetings/status` →
  - not configured / flag disabled → `{ configured: false }`
  - else `{ configured: true, canBook: boolean, meeting?: { startTime, cancelUrl, rescheduleUrl } }` from `findActiveMeeting(req.user.email)`. Supports `?fresh=1` (skip cache) for the post-booking refetch.
- `POST /api/meetings/booking-link` →
  - not configured → `409 { error: 'not configured' }`
  - gate re-check: `findActiveMeeting` (fresh, not cached) returns a meeting → `409 { error: 'active meeting exists' }`
  - else `{ bookingUrl }` from `createSingleUseLink()`.
  - Calendly API failure → `502`.
- The user's email comes from the verified JWT identity (`AuthRepository.findUserById(req.user.id).email`) — never from the request body.

## Frontend

### `src/components/sections/MeetUsSection.tsx` (new)

Rendered on the homepage alongside the other sections, **only when** `useAuthOptional()` has a user **and** the `meetUs` flag is enabled. Hebrew-first (i18n keys in `he.json` + `en.json`).

States, driven by `api.meetings.status()`:
1. **Not configured** (`configured: false`) → render nothing.
2. **Can book** → blurb + "קבעו פגישה איתנו" button → `api.meetings.bookingLink()` → open **Calendly popup embed** (`Calendly.initPopupWidget({ url })`, script loaded lazily on first click from `https://assets.calendly.com/assets/external/widget.js`), with `?name=<user.name>&email=<user.email>` prefill appended.
3. **Has meeting** → "יש לך פגישה ב־<date>" + cancel / reschedule links (`target="_blank"` to Calendly's pages) + note that cancelling frees the slot.
4. On the embed's `calendly.event_scheduled` window message → refetch status with `fresh=1` → state flips to 3. Toast on booking-link failure (409 → "כבר יש לך פגישה פעילה", 502 → generic failure), via `useToastOptional`.

### `src/lib/api-client.ts`

- `api.meetings.status(fresh?: boolean)` → `GET /meetings/status[?fresh=1]`
- `api.meetings.bookingLink()` → `POST /meetings/booking-link`
- `api.admin.featureFlags.update(name, { enabled, value })` → `PUT /admin/feature-flags/:name`

## Booking flow (end to end)

1. Signed-in member sees the section → `GET /api/meetings/status` → `canBook: true`.
2. Click book → `POST /api/meetings/booking-link` → backend re-checks the gate live → issues a single-use Calendly link → popup opens prefilled.
3. Member picks a slot in Calendly; Calendly creates the meeting (and Zoom link / location per the event type) and emails both sides. **Nothing written to our DB.**
4. Embed fires `event_scheduled` → frontend refetches (`fresh=1`) → section now shows the meeting + cancel/reschedule links. The single-use link is consumed (`max_event_count: 1`), so it can't be reused even if leaked.
5. Member cancels on Calendly (their link or our surfaced `cancelUrl`) → next status query finds no active event → booking re-enabled. No expiry logic needed: a past meeting simply stops matching `min_start_time=now`.

## Known accepted limitations

- **Prefill is editable:** a member can change the email inside the Calendly form; the gate (keyed to their account email) won't see such bookings. Acceptable for a small closed, invited group; revisit only if abused.
- **Public event-type URL:** anyone holding the Calendly event's public URL can book directly on Calendly, bypassing our gate. Inherent to Calendly; the broker adds the gate + prefill for members, not secrecy.
- **Calendly outage** ⇒ section shows an error state (gate cannot be checked, so booking is refused, `502`), never an open gate.

## Error handling

- Token unset / flag disabled / empty event-type URI → `configured: false`, section hidden; no errors, no Calendly calls.
- Calendly 4xx/5xx → logged `[meetus]`, route returns `502`; UI toast.
- Double-booking race (two tabs) → second `POST` re-checks live and gets `409`; worst case Calendly itself holds two bookings only if both popups were opened before either booked — accepted (closed group; visible in Calendly dashboard).
- `401` (not signed in) → impossible via UI (section hidden), API answers normally via `requireAuth`.

## Testing

- **`calendly.ts`** (mock `fetch`): unconfigured ⇒ `isConfigured` false, no HTTP; `findActiveMeeting` maps events+invitee URLs, returns null when none; cache hit within 60 s, bypass with fresh, bust on `createSingleUseLink`; `createSingleUseLink` posts correct body, returns `booking_url`; HTTP error ⇒ typed throw.
- **`meetings` routes** (supertest, mocked service + `requireAuth`): unconfigured ⇒ `{configured:false}` / `409`; active meeting ⇒ `canBook:false` + meeting fields, booking-link `409`; happy path `{bookingUrl}`; service throw ⇒ `502`.
- **Admin flags route:** `PUT` updates via `setFlag`, `400` invalid body, `requireAdmin` enforced.
- **`MeetUsSection`** (happy-dom): hidden when anonymous/disabled/unconfigured; book button calls `bookingLink`; existing meeting renders date + links; 409 → toast.

## Operator prerequisites (manual, one-time)

1. Create a Calendly account (Free works) + one event type (location = Zoom or in-person; this also decides 1-on-1 vs round-robin vs panel — Teams plan needed for round-robin).
2. Generate a personal access token → `CALENDLY_API_TOKEN` on Render.
3. Find the event-type URI (`GET /event_types?user=<me>`) → set it as the `meetUs` flag value + enable the flag in the admin panel.

## Out of scope (YAGNI)

- Webhooks / lock table (see Decisions).
- In-app cancel/reschedule (Calendly pages do it).
- Multiple meeting types per member, waitlists, host-side dashboards.
- Enforcement against prefill-email evasion.
